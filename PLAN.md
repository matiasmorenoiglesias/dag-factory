# Plan: dag-factory como herramienta de build, no de runtime

## Propuesta

Cambiar el paradigma de uso de dag-factory: de una librería que vive en producción a una **herramienta de build** que corre en desarrollo y CI/CD, generando archivos `.py` estáticos que Airflow consume sin depender de dag-factory.

## Modelo objetivo

```
Hoy:
  YAML → dag-factory (en producción, cada ciclo) → DAG objects → Airflow

Propuesto:
  YAML → dag-factory (en CI/CD, solo al cambiar) → .py generados → Airflow
```

## Flujo de trabajo

```
1. Developer edita o crea un archivo YAML
2. Abre un PR en Git
3. CI ejecuta dag-factory como CLI sobre los YAMLs modificados
4. dag-factory genera un archivo .py por cada DAG
5. Los .py generados se revisan en el PR (code review del DAG real)
6. Al mergear, los .py se suben al directorio/bucket que Airflow monitorea
7. Airflow solo ve y parsea archivos .py estáticos — sin dag-factory instalado
```

## Lo que hay que construir

### 1. Comando CLI `generate`

Agregar un nuevo subcomando a la CLI existente de dag-factory (ya usa Typer):

```bash
dagfactory generate --input ./dags/yaml/ --output ./dags/generated/
```

**Comportamiento:**
- Escanea recursivamente `--input` buscando archivos `.yaml` / `.yml`
- Por cada YAML genera un `.py` en `--output` con el DAG ya definido estáticamente
- Si un YAML no cambió (por hash o mtime), no regenera el `.py` correspondiente
- Reporta qué archivos fueron generados, cuáles fueron saltados y cuáles fallaron

**Archivo generado de ejemplo (`my_dag.py`):**
```python
# AUTO-GENERATED by dag-factory — do not edit manually
# Source: dags/yaml/my_dag.yaml
# Generated: 2024-04-09T10:00:00

from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

with DAG(
    dag_id="my_dag",
    schedule_interval="@daily",
    start_date=datetime(2024, 1, 1),
    catchup=False,
) as dag:
    task_a = PythonOperator(
        task_id="task_a",
        python_callable=...,
    )
    task_b = PythonOperator(
        task_id="task_b",
        python_callable=...,
    )
    task_a >> task_b
```

El `.py` resultante **no importa dag-factory** — es un DAG de Airflow puro.

---

### 2. Generador de código Python

Módulo interno `dagfactory/codegen.py` que toma el diccionario de configuración de un DAG (ya procesado por `DagBuilder`) y produce el código Python equivalente como string.

**Responsabilidades:**
- Traducir la config del DAG a código Python legible
- Resolver los imports necesarios según los operadores usados
- Formatear el output con `black` o similar para que sea legible
- Manejar casos especiales: `task_groups`, `dynamic task mapping`, callbacks

---

### 3. Integración CI/CD

Documentar y proveer un ejemplo de GitHub Actions que:

```yaml
# .github/workflows/generate-dags.yml
on:
  push:
    paths:
      - 'dags/yaml/**'

jobs:
  generate:
    steps:
      - uses: actions/checkout@v4
      - run: pip install dag-factory
      - run: dagfactory generate --input dags/yaml/ --output dags/generated/
      - run: git add dags/generated/ && git commit -m "chore: regenerate DAGs"
      - run: git push
```

O alternativamente, subir los `.py` directamente a un bucket S3/GCS que Airflow monitorea.

## Consideraciones

- **Backwards compatibility** — `load_yaml_dags` sigue funcionando. El nuevo comando es aditivo.
- **Validación en build time** — los errores de YAML se detectan en CI antes de llegar a producción.
- **dag-factory deja de ser una dependencia de producción** — solo se necesita en el entorno de desarrollo y CI.
